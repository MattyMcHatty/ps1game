PS1 HORROR GAME — TEXTURING A LEVEL: WHAT WE LEARNED
=====================================================
Written after texturing kitchen_dining. This documents the problems we hit and
the working pipeline, so we don't have to rediscover any of it.

Files involved (kitchen example):
  tools/io_export_smx_v3.py            - the Blender SMX exporter (master copy)
  assets/kitchen_dining.smx/.smd       - mesh (XML export -> binary)
  src/kitchen_dining_tex_map.h         - per-primitive texture index table
  src/kitchen_dining.c                 - loads textures + renders them
  textures/*.png -> *.tim              - the textures
  disc.xml                             - packs the .tim/.smd onto the disc


==========================================================================
PART 1 — THE TWO HARD PROBLEMS (and the fixes)
==========================================================================

PROBLEM A: The level hard-crashed the moment it tried to load.
--------------------------------------------------------------
Symptom: emulator crashed entering the kitchen (both via the door and the
debug menu), before the loading screen even appeared.

How we found it: bisection. We isolated that:
  - The new SMD was fine (rendered flat with no textures = OK).
  - 1, 2, 3 texture loads worked; the 4th crashed.
  - It crashed regardless of WHICH texture, its VRAM coords, or the CD audio
    callback. Loading the SAME texture 4x still crashed.
  - KEY CLUE: delivery_area loads 4 textures (8 LoadImage calls) at STARTUP and
    works fine — the exact same operation count that crashed mid-game.

ROOT CAUSE:
  LoadImage() (uploading a texture to VRAM) is only safe at STARTUP, before the
  main render loop begins. Once the per-frame VSync/draw cycle is running,
  flip_buffers() kicks off DrawOTagEnv asynchronously, and calling LoadImage
  while drawing is in flight collides on the GPU and hard-crashes after a few
  calls. delivery_area only gets away with it because it loads before the loop.

THE FIX:
  Load ALL of a level's textures ONCE AT STARTUP, never during the level
  transition. We added kitchen_load_textures(), called from main() right after
  delivery_area_init(), before the main loop. kitchen_dining_init() (run on the
  transition) now only loads GEOMETRY (a CD read, no LoadImage), which is safe.

  Because each level's textures live in non-overlapping VRAM regions, every
  level's textures can be resident at the same time — so loading them all up
  front is fine.

  >>> RULE: every new level needs a <level>_load_textures() called at startup in
      main(). Do NOT call LoadImage mid-game.


PROBLEM B: Textures didn't match the Blender UV mapping (looked wrong/smeared).
-------------------------------------------------------------------------------
Symptom: the level loaded with textures, but surfaces didn't look like Blender —
the engine was ignoring the Blender UVs.

Two sub-issues:

  B1) The old renderer (copied from delivery_area) used PROCEDURAL UVs: it
      projected UVs from world position + face normal and ignored the model's
      real UVs entirely. Fine for plain tiled floors/walls, wrong for anything
      mapped deliberately (furniture, doors).

  B2) PS1 stores texture coordinates as 8-BIT (0-255). Blender UVs tile heavily,
      so the raw exported values are large/negative (e.g. -497, -1004). When
      those get truncated to 8 bits, any polygon whose UVs cross a 256-texel
      boundary gets DISTORTED (coords wrap mid-polygon and interpolate wrong).

THE FIX (two parts):

  1) EXPORTER (io_export_smx_v3.py): output 8-bit-safe UVs.
     - Scale UVs to a fixed target texel size (exp_tex_size, default 128) rather
       than the Blender image resolution. UVs are normalized per tile, so the
       source image's pixel size is irrelevant; 1 UV tile = 128 texels.
     - For each polygon, shift its UVs DOWN by whole tiles (multiples of 128) so
       the minimum lands in [0,128). This keeps values 8-bit-safe AND preserves
       the sub-tile phase (multiples of 128), so tiling stays continuous across
       adjacent faces.

  2) RENDERER (kitchen_dining.c): use the real UVs + a hardware texture window.
     - Read the per-poly UVs straight from the SMD primitive (FT4 stride 32:
       tu0,tv0..tu3,tv3 at byte offsets 20-27) into the POLY_FT4.
     - Add a 128x128 TEXTURE WINDOW (DR_TWIN) so UV values past the texture edge
       WRAP (tile) within the texture's page instead of reading neighbouring
       VRAM. SDK RECT is {0,0,16,16} for the 128 window every room uses.

       >>> DO NOT compute the mask as texels>>3. That formula is a COINCIDENCE
           that holds at 128 and 256 and is WRONG everywhere else. The field is
           "bits to CLEAR, >>3", not a size: the GPU does
               u' = (u & ~(mask<<3)) | ((offset & mask)<<3)
           so the mask must be of the form (256-size)>>3:
               mod 128 -> 16     mod 64 -> 24     mod 32 -> 28
               mod 256 ->  0 (no wrap at all)
           64>>3 = 8 does NOT wrap at 64; it clears bit 6 and leaves bit 7.

       >>> RECT.x/y are an OFFSET (also in 8-texel units), letting the window
           address a SUB-RECT of the page. It is the escape hatch behind
           tools/subpack_uvs.py (PART 5).
     - The DR_TWIN is sorted at OT_LENGTH-1 and the textured polys are clamped to
       OT_LENGTH-2, so the window is applied by the GPU before any textured poly.

  REMAINING LIMIT: a single face that tiles a texture MORE than once across
  itself (UV span > 1 tile on one polygon) can still show a seam — that's the
  8-bit hardware limit. Fix by mapping such faces to <= 1 tile in Blender.


==========================================================================
PART 2 — VRAM / TEXTURE FORMAT RULES (learned the hard way)
==========================================================================

- 8bpp textures: a texture PAGE is only 128 texels wide. A 256-wide 8bpp
  texture spills across page boundaries and renders wrong / can crash. So:
  >>> Keep textures 128x128 (8bpp). We resized the oversized ones down.
  >>> The 128 WIDTH is hardware at 8bpp. The rest of this rule is not: a texture
      SMALLER than 128 can share a tile with three others — see PART 5.

- Texture page X must be a multiple of 64; page Y must be 0 or 256.
  >>> Place textures at x in {320,384,448,576,...} (64-aligned) and y in {0,256}
      (page-aligned), or UVs sample the wrong region.

- CLUTs (256-colour, 256 words wide x 1) go in the VRAM scratch area below the
  framebuffers (y >= 480), away from the framebuffers (x<320, y<480), the font
  (x>=960), and all other textures.

- VRAM map at the time of writing (avoid overlap when adding more):
    Framebuffers: x[0,320)  y[0,480)
    Font:         x[960,1024)
    Delivery/props textures: x[512,960) (gravel, fence, brick, door, crucifaxe,
                  dogs, key, shadow, sml_med, crate, etc.) — see each TIM's coords
    Kitchen textures (this work): images x[320,640) y{0,256}; CLUTs x=0 y489-496


==========================================================================
PART 3 — STEP-BY-STEP: TEXTURING A NEW LEVEL
==========================================================================

In Blender:
  1. UV-map the mesh. Keep each face's UV span to about ONE texture tile to
     avoid PS1 seams (tiling across many faces is fine; tiling within one face
     past 1x is not).
  2. Assign textures via materials (image texture node).
  3. Export with tools/io_export_smx_v3.py (File > Export > Scarlet SMX v3).
     Leave "Texture Size" = 128. Save as assets/<level>.smx.

Convert + register the textures:
  4. For each texture PNG, make a 128x128 8bpp TIM at a free, page-aligned VRAM
     slot (64-aligned X, Y in {0,256}), CLUT in the y>=480 scratch area:
       python textures/png_to_tim.py NAME.png --bpp 8 --tx <X> --ty <Y> \
              --cx <CX> --cy <CY> --out NAME.tim
  5. Add each TIM to disc.xml (8.3 uppercase name -> source path).

Convert the mesh:
  6. smxlink -tp textures -o assets/<level>.smd assets/<level>.smx
     (the -tp lets it resolve the texture references).

Generate the texture map (per-primitive texture index), e.g.:
  7. A small Python script reads each <poly>'s texture="N" from the .smx in
     order and writes src/<level>_tex_map.h (uint8 array, 0xFF = untextured).
     See how kitchen_dining_tex_map.h was generated.

Engine code (model on kitchen_dining.c):
  8. tex_tpage[]/tex_clut[] arrays; load_tim_buf() loads each TIM via a single
     shared scratch buffer.
  9. <level>_load_textures() loads them ALL — call it at STARTUP in main(),
     NOT in the level's init. (See PROBLEM A.)
 10. In the SMD draw loop, for textured quads: read UVs from the prim (offset
     20-27), set tpage/clut from the slot, emit POLY_FT4.
 11. In the level's draw(): sort a 128x128 DR_TWIN texture window at OT_LENGTH-1
     and clamp poly OT indices to <= OT_LENGTH-2.

Build:
 12. cmake --build build --target horror_game   (auto-runs elf2x)
     mkpsxiso -y disc.xml
     (See "rebuild commands.txt".)


==========================================================================
PART 4 — DEBUGGING TIPS THAT WORKED
==========================================================================

- A hard crash with NO loading screen = the crash is in the level's init
  (the loading screen is drawn but only shown by the flip AFTER init returns).
- To localize a load/render crash, bisect: render flat (ignore textures) vs
  load textures; load 1 vs many; same texture vs different; with/without the
  SMD load. Each isolates one variable.
- "Looks identical after a rebuild" usually means a STALE binary — verify
  build/HORROR2.BIN and build/HORROR.bin timestamps are newer than the source.
  (elf2x must run to turn HORROR.exe into the HORROR2.BIN the disc boots.)


==========================================================================
PART 5 — TEXTURE-WINDOW HYGIENE  (the "wrong texture in one room" class of bug)
==========================================================================
The texture window is PERSISTENT GPU state: a DR_TWIN sorted into the OT stays
in effect for every later primitive (and every later FRAME) until another DR_TWIN
changes it. Kitchen and reception sort a 128x128 window at OT_LENGTH-1; that
window then applies to everything drawn below it AND leaks into whatever is drawn
next unless reset — including overlays (the menu) and, across a room change, the
next area (delivery uses no window of its own).

WHY IT BITES: a 128 window wraps texture coords mod-128. Any texture whose VRAM y
puts it at V-offset >= 128 within its 256-tall tpage (see the "Voff" column in
tools/VRAM_MAP.txt) then samples 128 texels too high — i.e. the WRONG texture
sitting above it in the page. Symptom: an icon/sprite looks fine in the delivery
area but wrong (and DIFFERENT) in each windowed room, depending on what art
happens to sit above it in VRAM. (This was the crucifaxe/key menu-icon bug and
the reason delivery must reset the window on return from a room.)

RULES:
  1. Every area's draw() OWNS its texture-window state — set it explicitly, never
     inherit it. Windowed rooms sort the 128 window at OT_LENGTH-1; delivery (no
     window) sorts a full-reset RECT{0,0,0,0} so a stale room window can't leak in.
  2. Any overlay or sprite drawn OVER a windowed room (menu icons, entity
     sprites/shadows) that uses a Voff>=128 texture must reset/bracket the window
     it needs. Menu: one full-reset DR_TWIN above the icons. Zombies: bracket each
     sprite with a full-window reset + restore (zombie.c add_ft4_windowed).
     door_anim: sets its own RECT{0,0,0,0} for its Voff-128 half-door panels.
  3. Demon dogs currently draw WITHOUT a bracket, so they are only safe in the
     delivery area (no window). Moving them into a windowed room requires the
     zombie-style bracket first (noted in demondog.c).
  4. Keep new window-sensitive art at Voff 0 (VRAM y 0 or 256) when you can — it
     sidesteps the whole issue. Check tools/VRAM_MAP.txt after placing a texture.
  5. A single reset sorted a few OT buckets ABOVE your content is NOT reliable
     inside the shared UI block 0-15 — something else can land in between and
     re-enable the window. Disable it in the SAME OT bucket as the content,
     after that bucket's prims, the way zombie.c's add_ft4_windowed does. The
     HUD learned this the hard way; see tools/HUD_NOTES.txt PART 3b.


==========================================================================
PART 6 — ALPHA IS A THRESHOLD, AND THE DEFAULT EATS UI BORDERS
==========================================================================
The PS1 has no partial alpha: a texel is drawn or skipped. png_to_tim.py
therefore thresholds the source alpha, and its default cut is 128.

That is right for SPRITES — a half-covered antialiased edge is a soft halo you
want gone. It is WRONG for hand-drawn UI line art: a 1-2px box border drawn at
50% coverage falls below the cut and disappears entirely, leaving boxes with
missing edges. This ate the top edge of every box on the HUD panel.

  >>> RULE: UI panels convert with --alpha-cut 1 (keep anything not fully
      transparent). Sprites and world textures keep the default 128.

Either way, decode the .tim back and compare it to the source before trusting
it. A missing 1px line is invisible in a thumbnail and glaring on a TV.


==========================================================================
PART 5 — BREAKING THE 128x128 RULE: SUB-PACKING SMALL TEXTURES
==========================================================================
"Every texture must be 128x128" is THREE constraints wearing one hat, and only
one of them is hardware:

  HARD    An 8bpp texture page is 64 VRAM halfwords = 128 texels WIDE. Nothing
          gets past that at 8bpp. (A 4bpp page is 256 texels wide.)
  SOFT    io_export_smx_v3.py scales every UV in an export to ONE texel size
          (exp_tex_size = 128), for the WHOLE export. This — not the hardware —
          is why a 64x64 source has to be stretched to 128x128.
  SOFT    Each room sorts ONE DR_TWIN at OT_LENGTH-1, so one window serves every
          texture in the room.

So a small texture currently burns a full 64x128 VRAM block for detail it does
not have. tools/subpack_uvs.py fixes that WITHOUT touching either soft rule.

HOW IT WORKS
  It runs on the .smx BEFORE smxlink and rewrites the UVs of chosen textures
  from the 128 tile the exporter emitted onto a sub-rect of that same tile:

      u' = round(u * size / 128) + u_off

  Four 64x64 textures then share ONE 128x128 footprint at a quarter of the VRAM
  each (an eighth at 4bpp), and each keeps its OWN CLUT — `clut` is a per-poly
  field and each sub-texture is still its own TIM.

  NO C CHANGE IS NEEDED, for two reasons worth understanding:
    - The room's mask-128 window leaves any UV already in [0,128) completely
      alone, and the sub-rect is inside that range. No bracket, no second
      DR_TWIN, no per-poly window.
    - The sub-TIM sits at a NON-page-aligned tx inside the tile, so getTPage()
      floors to the SAME tpage as its neighbours. tex_tpage[]/tex_clut[] get
      the ordinary one entry per texture and nothing else changes.

THE PRECONDITION — THE TEXTURE MUST NOT TILE
  Wrapping is mod 128 across the WHOLE tile, so a sub-texture that tiles would
  wrap into its neighbour. Any texture with a UV over 128 is REFUSED. Most
  wall/floor textures tile; small props and decals usually do not. Check with:

      python tools\subpack_uvs.py --report assets\garden\Greenhouse.smx

  Sub-packing also costs the far-edge texel: a full-tile span of 0..128 becomes
  0..63, because a sub-rect cannot wrap. That is a half-texel inset, invisible.

THE OTHER TRAP — SHARED TEXTURES
  A TIM is global. Packing a texture in one level while another level still
  addresses the full 128 tile makes that other level sample the new neighbour.
  --report names every level that shares each texture; pack it in all of them
  or in none. (grss is in 12 levels; poison_flower_base is in 4.)

STEPS
  1. Report, and pick textures that neither tile nor are shared:
       python tools\subpack_uvs.py --report assets\<Level>.smx
  2. Write a table, e.g. tools\subpack\<level>.json — see the script's header
     for the format. Entries sharing a "page" label are checked for overlap.
  3. Pack (the input is never modified; output is <Level>.packed.smx):
       python tools\subpack_uvs.py assets\<Level>.smx tools\subpack\<level>.json
  4. Re-make each packed texture as a TIM at its real size, inside the tile:
       8bpp:  --tx <page_x + u_off/2>   --ty <page_y + v_off>
       4bpp:  --tx <page_x + u_off/4>   --ty <page_y + v_off>
     page_x stays 64-aligned and page_y in {0,256}; the sub-TIM's own tx is
     deliberately NOT page-aligned.
  5. GREP THE C FOR HAND-WRITTEN UVs ON THAT TEXTURE. This pass rewrites MESH
     UVs only. Anything that draws the texture from UV CONSTANTS in C still
     spans the old 128 tile and will read off the end of the shrunk texture into
     whatever shares its page.
       >>> This bit us. `greenhouse door` shrank to 64x64 and the mesh was fine,
           but DOOR_PANEL_GREENHOUSE in src/door_anim.c draws the transition
           panel from GH_U_HINGE/GH_V_BOT, still 127. Three quarters of the panel
           sampled frnt_dr/red_crpt/dbl_dr_rg beside it and the transition showed
           a double-door texture. The fix is to halve the constants, not the TIM.
       grep -rn "TIM_TPAGE_<SLOT>" src/*.c    and check every hit's UV constants.

  6. Convert from the PACKED file:
       smxlink -tp textures -o assets\<Level>.smd assets\<Level>.packed.smx
  6. Re-run tools\vram_map.py and CHECK IT. It assumes 128x128 everywhere, so
     teach it the new extents or its collision check is quietly lying to you.

  Re-exporting from Blender overwrites the source .smx, so step 3 is re-run
  after every export. The tex-map generator may read either file — this pass
  changes no texture list, no poly order and no poly count.

GOING THE OTHER WAY — BIGGER THAN 128
  Only ONE dimension can grow, and only at 4bpp: a 4bpp page is 256 texels wide,
  so 256x256 fits exactly one tpage. At 8bpp 128 is the hard ceiling on WIDTH.
  subpack_uvs.py accepts "size": 256 and doubles the UVs for you.

  >>> BUT THE EXPORTER'S TILING SCHEME CANNOT FEED A 256 TEXTURE, AND THIS IS
      THE THING TO UNDERSTAND BEFORE YOU TRY. The exporter leaves each face's UV
      minimum in [0,S) and relies on the texture window to wrap anything past the
      edge, so the maximum reaches S+span:

        S=128 -> max <= 192.  Fits 8 bits, and the mask-128 window wraps it.
        S=256 -> max <= 320.  DOES NOT FIT 8 BITS, and a 256 texture has no
                              window that can wrap it (mask 0 = no wrap, and the
                              UV field is 8-bit, so the value is simply lost).

      A face that straddles a tile edge therefore CANNOT be represented. The tool
      shifts it the rest of the way, which fits it but lands it on a different
      part of the art. WE SHIPPED THAT ONCE: the Greenhouse's `cuniform pipes`
      went 4bpp 256x256, 16 of its 40 faces straddled, and the pipes lost their
      symbols. It was reverted to 8bpp 128x128.

      So a 256 texture needs a UV layout where NO FACE CROSSES A TILE EDGE. That
      is a Blender job, not a tooling one: keep every face for that material
      inside one 0..1 tile, re-export, and THEN pack. Check the straddle count in
      the pack report before believing it worked — if it is not zero, stop.

  IF YOU DO GET A CLEAN 256 LAYOUT, it still costs four things, all of which the
  cuniform pipes attempt actually hit and solved before the UV problem sank it:
    1. A WHOLE TPAGE — 64 units x 256 ROWS, i.e. BOTH Voff halves. That breaks
       the Voff-0/Voff-128 sharing the VRAM map is built on. There is almost
       certainly nothing free: every y0 page's lower half had a real occupant,
       and every y256 page is disqualified because the CLUT band at y[480,512)
       runs through it. Check BOTH halves before planning.
    2. A RESTORE OBLIGATION for whatever you displace — and check what the room's
       own door transitions draw, since a door panel's page is the worst thing to
       take. (512,0)'s lower half is dbl_dr_hlf, i.e. DOOR_PANEL_OUTER.
    3. A PER-POLY BRACKET, because the room's mask-128 window would wrap 0..255
       UVs at 128 and draw the left half twice. Window off before the poly, the
       128 window after — src/copper_pot.c's shape. Reserve both DR_TWINs in the
       buffer check as well as the poly.
    4. A BIGGER STREAM BUFFER: 4bpp 256x256 is 32832 bytes = 17 sectors against
       16928 for an 8bpp 128x128. Run tools/heap_budget.py.
    ...and 16 colours, since 4bpp is forced.

  THE CHEAP ALTERNATIVE, if all you want is horizontal density: 4bpp 256x128 is
  64 units x 128 rows — EXACTLY an 8bpp 128x128's footprint. No page to find, no
  restore, no bracket, no scratch growth. It is the right trade whenever the art
  is used wider than it is tall; compare the max U span against the max V span
  first. (For cuniform pipes it was the wrong way round: U span 19, V span 32.)

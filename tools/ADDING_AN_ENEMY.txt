PS1 HORROR GAME — ADDING A NEW ENEMY: THE COMPLETE RUNBOOK
============================================================
This is the authoritative, step-by-step procedure for adding a reusable sprite
enemy. It was written immediately after the Spider was added (July 2026) and
records every step that was actually performed, in order, with real commands —
including the two things that were got WRONG first time (see the last section).

>>> IF THE ENEMY IS A 3D MODEL RATHER THAN A SPRITE, read this file first and
    then tools/ADDING_A_3D_ENEMY.txt, which records the delta (the composed
    model-view matrix, the foot offset, the cylinder collision, the
    surface-distance melee reach, and why STEP 3 below does not apply). <<<

Companion docs (read them for the *why*; this file is the *how*):
  tools/ADDING_A_3D_ENEMY.txt       - the MODEL-enemy delta against this file
  tools/ADDING_A_BOSS_ENCOUNTER.txt - what to do AFTER the enemy exists, if it
                                      is a boss: camera, reveal, sealed arena,

##########################################################################
 HOW TO KICK THIS OFF (what the user provides)
##########################################################################
To start an enemy addition, the user only needs to say:

  1. "Follow tools/ADDING_AN_ENEMY.txt"
  2. The enemy's name, e.g. "Spider" -> slug `spider`.
  3. The texture names, already dropped in textures/ as PNGs,
     e.g. spdr_rst.png (at rest) and spdr_wk.png (moving).
  4. Its behaviour in prose: sprite shape/scale, health, what wakes it,
     how it moves and attacks, what each weapon does to it.
  5. Where to place it: room + x/z coordinates.

Everything else — VRAM slots, CLUT lines, sprite half-extents, ceiling/floor
heights, nav wiring — is DERIVED by the steps below. Do not ask the user for
heights; mine them out of the .smx (STEP 2).

Naming: a lowercase C slug (spider) for src/<slug>.c/.h and a SHORT uppercase
prefix for the constants (SPD_). Keep the prefix distinct from the existing ones
(ZMB_, DDOG_, VAMPIRE_, TENTACLE_).

NOTE ON PYTHON: the `python` on PATH is the Windows Store stub and fails. Use
`py` (works, has Pillow) or the real interpreter explicitly:
    C:\Users\virtu\AppData\Local\Python\bin\python.exe


##########################################################################
 STEP 1 — READ THE ENEMY YOU ARE COPYING
##########################################################################
There are two enemy archetypes. Pick the one whose PERSISTENCE model fits, then
copy the other's behaviour code as needed.

  src/zombie.c    <- THE reference enemy. Full-featured: DORMANT/ALERT/DEAD,
                     feeler steering with wall-follow commit, separation,
                     body-vs-body push, knockback, fat-door battering, a room
                     nav graph, health bar, fog, texture-window bracketing.
                     Copy its update/draw structure verbatim and delete what
                     the new enemy does not need.
  src/tentacle.c  <- the cheap archetype: ONE global array tagged by area, no
                     movement. Copy its PERSISTENCE model (see STEP 6).
  src/demondog.c  <- the delivery-area dog; note it does NOT bracket the
                     texture window and is only safe in windowless rooms.

What is load-bearing in the zombie's draw path and must be copied, not
redesigned: the avgZ OT sorting with the SCENE_OT_MIN clamp, the fog cull
against g_fog_far, the packet-space checks against buf_end, the one-texel UV
inset, and add_ft4_windowed().

The Spider kept: the state machine shape, steering, separation, knockback,
health bar, shadow, windowed draw. It dropped: the nav graph (it fights in the
room it lands in) and the lunge/bite overlay.


##########################################################################
 STEP 2 — MINE THE MESH FOR ANY HEIGHT THE ENEMY NEEDS
##########################################################################
Only needed for an enemy that attaches to level geometry (a ceiling-dweller, a
wall-crawler). A plain floor enemy skips to STEP 3.

>>> READ THE MESH THAT IS ACTUALLY DRAWN, NOT THE COLLISION PROXY. <<<
Every room has two meshes and they DO NOT AGREE on height:
    assets/<Name>.smx        the VISUAL mesh -> <slug>.smd -> what you see
    assets/<Name> mesh.smx   the COLLISION proxy -> src/<slug>_mesh_collision.c
The proxy is simplified; its wall tops are only a LOWER BOUND on the ceiling.
For the East Hall the proxy tops out at y=-375 while the drawn ceiling is at
y=-520 — a 145-unit error, which is more than a spider's body length.

Find the real ceiling over a point with a throwaway script:

  import re
  s=open('assets/East Hall.smx',encoding='utf-8',errors='replace').read()
  vb=s.split('<vertices')[1].split('</vertices>')[0]
  vs=[(float(a),float(b),float(c)) for a,b,c in
      re.findall(r'x="([-\d.]+)" y="([-\d.]+)" z="([-\d.]+)"',vb)]
  P=(2132.0,354.0)
  for m in re.finditer(r'<poly ([^/]*)/>',s):
      at=dict(re.findall(r'(\w+)="([^"]*)"',m.group(1)))
      ids=[int(at[k]) for k in ('v0','v1','v2','v3') if k in at]
      pts=[vs[i] for i in ids]; ys=[p[1] for p in pts]
      if max(ys)-min(ys)>1: continue          # horizontal planes only
      xs=[p[0] for p in pts]; zs=[p[2] for p in pts]
      if min(xs)<=P[0]<=max(xs) and min(zs)<=P[1]<=max(zs):
          print('plane y=%.0f'%ys[0], 'x[%.0f,%.0f]'%(min(xs),max(xs)),
                                      'z[%.0f,%.0f]'%(min(zs),max(zs)))

Then record the value on the ROOM, next to its collision init:

  src/<room>.c:  <room>_collision_init(&current_collision_room);
                 collision_set_ceiling_y(-520);   /* drawn ceiling; proxy
                                                     walls stop at -375 */

Every other room must call collision_set_ceiling_y(0) at the same place —
0 means "derive it from the wall tops" (collision_ceiling_y falls back to the
highest wall top within CEILING_PROBE_R). The generated *_collision_init() does
NOT touch the field, so a room that stays silent inherits the previous room's
ceiling. This is exactly the r->multi_level / r->shoot_over_mask trap from the
room runbook, one field along.

COORDINATE CONVENTIONS (get these wrong and the enemy floats or sinks):
  east = +X, west = -X, north = +Z, south = -Z.  -Y is UP.
  Mesh floors are at y=0; ceilings are negative.
  Entity x/y/z are drawn as raw MESH coordinates — an entity y of -149 is a
    point 149 above the mesh floor. Sprite vertices and mesh vertices share
    one space, so a ceiling at mesh y=-520 is at entity y=-520. Do NOT apply
    GROUND_FLOOR_Y to it.
  GROUND_FLOOR_Y (149) converts a FloorZone's SURFACE into an entity's standing
    ANCHOR: apply_ddog_height() computes target = zone->y - GROUND_FLOOR_Y.
    That is a different job from a coordinate-space change. Applying it to a
    ceiling height is a bug (it was made — see the last section).


##########################################################################
 STEP 3 — TEXTURES
##########################################################################
Sprites are much easier than mesh art: they are drawn one quad at a time and
bracket their own texture window, so unlike room textures they MAY live at
Voff >= 128. That is where the free space is.

3a. Check the source PNGs. 8bpp is the norm for sprites. Power-of-two, and the
    art should fill the frame — transparent padding shows up as the sprite
    floating away from whatever it is attached to.

      py -c "from PIL import Image; im=Image.open('textures/spdr_rst.png'); \
             print(im.size, im.mode, im.getbbox())"

3b. Find VRAM slots in tools/VRAM_MAP.txt. A slot needs x a multiple of 64 and
    enough free rows. For two 128x128 8bpp sprites that is 64 words wide x 128
    tall each. The Spider took x[320,448) y[128,256), which was empty.
    Confirm the band is clear yourself; do not trust a stale map.

3c. CLUT lines: 8bpp needs 256 words, one line tall, at y >= 480. Look for a
    line whose only occupant is a 16-word 4bpp CLUT at x[0,16) and take
    x[256,512). The Spider used (256,492) and (256,493).

3d. Convert:

      Set-Location "c:\Users\virtu\Documents\ps1game\textures"
      py png_to_tim.py spdr_rst.png --bpp 8 --tx 320 --ty 128 --cx 256 --cy 492
      py png_to_tim.py spdr_wk.png  --bpp 8 --tx 384 --ty 128 --cx 256 --cy 493

3b-bis. IF THERE IS NO FREE SLOT — SHARE ANOTHER ENEMY'S. As of the Rafflesia
    (Aug 2026) VRAM has no 128-row hole left: the only free band is y[384,480)
    at x >= 800, which is 96 rows and runs into the CLUT band at y=480. A new
    128x128 pair must therefore TIME-SHARE an existing enemy's slots, and the
    rule for picking a donor is the same one the rooms use — pick something the
    new enemy can never be in a room with. The Rafflesia is a garden enemy and
    took the SPIDERS' two slots (x320/x384, y128), because spiders only exist
    inside the house.

    Sharing means neither sprite may be a plain startup LoadImage any more.
    Both enemies register their sprites with texmgr (a resident RAM copy) and
    expose a <slug>s_upload_textures(); main.c then streams exactly one of the
    two pairs in on EVERY room entry, in the STATE_LOADING block beside the
    room uploads and keyed on pending_area:

        if (pending_area == STATE_<ROOM>) <new>s_upload_textures();
        else                              <donor>s_upload_textures();

    An `else` and not a second `if`: the donor must come back on every other
    entry, including title-screen loads and debug level-select jumps, which all
    pass through that same line. Watch TEXMGR_MAX — converting the donor costs
    registrations too, and the count was at exactly 48 when this was written.
    CLUTs do NOT have to be shared (lines are cheap; give the new pair its own),
    and finally add the pair to SHARED_SLOTS in tools/vram_map.py with a comment
    saying which room separates them, or the map will report the overlap as an
    unexpected collision forever.

3e. Regenerate the map and CHECK IT:

      py tools\vram_map.py | Out-File -Encoding utf8 tools\VRAM_MAP.txt
      Select-String tools\VRAM_MAP.txt -Pattern "UNEXPECTED|No unexpected"

    Want "No unexpected pixel collisions." plus your two textures listed with
    the CLUT coordinates you asked for.


##########################################################################
 STEP 4 — THE ENEMY MODULE (src/<slug>.c / .h)
##########################################################################
Copy src/zombie.c/.h and rename. The header is the tuning sheet: every constant
gets a comment saying what it is in world units and why it has that value.

  Sprite extents
      <PFX>_HALF_W / <PFX>_HALF_H are HALF-extents in world units. The zombie is
      62 x 125 (a 1x2 body). The Spider is 93 x 62 (a 3x2 body) at "roughly the
      same scale". Pick <PFX>_Y_OFFSET so that Y_OFFSET + HALF_H equals the
      zombie's 150 — that is the distance from the entity anchor down to the
      feet, so the new enemy stands on the floor like every other one.

  load_tim() / <slug>s_load_textures()
      Copied verbatim. LoadImage is STARTUP ONLY (see TEXTURING_NOTES) — call
      it from main() before the render loop, never on a transition.

  State machine
      DORMANT / ALERT / DEAD at minimum. Add states for anything with a
      transition animation (the Spider adds CEILING and DROPPING).

  update_<slug>s()
      Order matters: tick timers, then apply_ddog_height() for gravity/floor,
      then the knockback branch (which `continue`s), then wake test, then the
      contact-damage test, then `if (dist2d < CATCH_DIST) continue;`, then
      steering, then the move + collision calls. Finish with the
      enemy-vs-enemy separation pass AFTER every instance has moved.

      Contact damage: test horizontal and vertical reach SEPARATELY. A combined
      |dx|+|dz|+|dy| budget never fires, because the player's eye sits above the
      enemy's body and eats the whole budget. This bug has been fixed twice.

      Collision calls, in this order, after moving:
        apply_flat_entity_collision(&x,&z, BODY_RADIUS);
        crates_collide(&x,y,&z, 80);
        dining_tables_collide(&x,y,&z, 75);
        fatdoors_collide(&x,y,&z, DOOR_CLEARANCE);

  draw_<slug>s() / draw_<pfx>_sprite()
      Camera-facing billboard: right vector = (icos(cam_rot), -isin(cam_rot)),
      up = world Y. isin/icos are 4096 = 360 degrees in this SDK (the header
      doc claiming 131072 is wrong — cam_rot is masked & 4095 everywhere).

      To ROLL a sprite in its own plane (the Spider's upside-down hang and its
      turn on the way down), rotate the corner offsets before placing them:
        ru = (u*icos(a) - v*isin(a)) >> 12;
        rd = (u*isin(a) + v*icos(a)) >> 12;
        vx = cx + ((ru*rx)>>12);  vy = cy + rd;  vz = cz + ((ru*rz)>>12);
      Leave the UVs on the original corner indices — that is what makes the
      texture flip with the quad. And DROP the gte_nclip() backface cull the
      zombie does: past 90 degrees the winding reverses and the cull throws the
      whole sprite away. A camera-facing quad has no back face to cull anyway.

      A 180-degree roll is about the quad CENTRE, so it does not change the
      sprite's extent. Anchoring a hanging enemy means putting its TOP edge on
      the ceiling: y = ceiling - Y_OFFSET + HALF_H. Anchoring the centre buries
      the top half in the roof.

      Texture windows: any sprite whose VRAM Voff >= 128 MUST bracket its poly
      with a full/unmasked DR_TWIN and then a restore of the area's window, in
      the same OT bucket. Copy add_ft4_windowed() and the
      <slug>s_set_texwindow() setter verbatim.


##########################################################################
 STEP 4b — RANGED ATTACKS AND STATUS EFFECTS (optional)
##########################################################################
Only for an enemy that fights at range. The Spider added both together; either
can be used on its own.

BANDED AI. A kiting enemy picks its behaviour from its TRUE radial distance to
the player (squares, no sqrt — coordinates stay in the low thousands so they fit
an int32). Keep the Manhattan dist2d for the CONTACT reach test: that one wants
to match the sprite's own footprint, not a stated radius. The Spider's bands:

    d <= SPD_ATTACK_RADIUS (500)  close in and bite, full speed
    d <= SPD_SPIT_RADIUS   (800)  back off at HALF speed
    d >  SPD_SPIT_RADIUS          close the gap at full speed

Keep MOVEMENT and FIRING as separate decisions. The bands pick only where the
enemy walks; the Spider fires at any range beyond SPD_ATTACK_RADIUS, so both
outer bands spit and only the melee band holds fire. Folding the fire control
into one band's branch is the obvious first cut and it is wrong — it silently
disarms the enemy in every other band.

Restructure the steering to run off a goal VECTOR rather than the raw player
delta, because a retreating enemy's goal is the opposite direction:
    int32_t goal_dx = pursuing ?  dx : -dx;   /* and goal_dz */
Everything downstream must use it: the desired direction, the wall-follow
perpendiculars (pl_x = -goal_dz, not -dz), and the "which side gets me closer"
tie-break, which needs a goal POINT (s->x + goal_dx) instead of the player's.

>>> AND GATE THE LINE-OF-SIGHT SHORTCUT ON `pursuing`. <<<
The zombie/spider steering switches wall-following OFF when the sightline to the
player is clear. That reasoning only holds while moving TOWARD the player — the
sightline says nothing about what is behind a retreating enemy, so leaving it
ungated turns off wall-following exactly when the enemy is reversing blind into
a wall.

Bands are self-reinforcing and will not oscillate at the boundary: advancing
while inside the melee band drives d down, retreating while outside it drives d
up. Do not add hysteresis unless you have actually seen it flip.

PROJECTILES live in their own module (src/web.c/.h), not in the enemy's:
  - Fixed pool (MAX_WEBS), `life` frames as the free/used flag, tagged with a
    GameState so a shot cannot follow the player through a door.
  - TRANSIENT: no world.c wiring at all, exactly like the particles and
    bullet-hit sprites. Add a *_reset() to reset_game and nothing else.
  - Aim ONCE at spawn and travel straight. That is what makes it dodgeable:
    walking toward or away keeps the player on the line, strafing does not.
  - Normalise the aim with a real integer sqrt (isqrt32 in web.c). The Manhattan
    divide used all over the steering code is fine for a direction that only has
    to be roughly right, but it would make projectile speed vary ~40% with the
    firing angle.
  - Test the SEGMENT travelled each frame with collision_segment_blocked(), not
    the new point, so a fast projectile cannot tunnel through a thin wall.
  - Require a clear sightline before FIRING too, or an enemy will spit through
    the wall it is standing behind.
  - Drawing an untextured solid: transform the corners, emit POLY_F4s. If every
    face is the same flat colour you can skip backface culling entirely and put
    all faces at one OT depth — the silhouette is identical whichever face the
    GPU lays down first, and you avoid depending on getting the winding right
    for gte_nclip (see the mistakes list).

STATUS EFFECTS belong to the player, in player.c, as a frame countdown:
  - player_<effect>(void) applies/REFRESHES the timer (refresh, do not stack —
    two projectiles landing together should not double the lockout).
  - player_status_update() ticks it; call it beside weapons_update() in
    update_current_area, INCLUDING the camera-locked puzzle branches that return
    early, or the effect freezes mid-puzzle.
  - Do NOT gate the effect on DBG_INFINITE_LIFE. That toggle suppresses health
    loss only; attacks still land in every other respect.
  - Clear it in reset_game alongside bullet_hits_reset().
  - Movement hooks go in camera.c: halve `speed` after the sprint branch, and
    add the effect to the sprint condition so the lockout is independent of the
    stamina bar (which keeps refilling underneath, ready for when it wears off).
  - FULL-SCREEN TINT: copy the Grave-olver muzzle flash's TILE + DR_TPAGE pair,
    but use ADDITIVE blending (abr=1, as particles.c does) rather than the
    flash's 50/50. A 50/50 blend halves the scene underneath — fine for a
    two-frame flash, but over five seconds it reads as the lights going out
    rather than a status. Additive tints without darkening. Draw it from the
    player-systems pass BEFORE draw_hud so the HUD stays untinted, at an OT
    index below SCENE_OT_MIN but above the HUD's (the Spider used 3).


##########################################################################
 STEP 5 — WEAPONS
##########################################################################
Expose ONE damage entry point from the enemy header and let both weapons call
it, so "wake on damage", the health-bar flash, death, particles and sound live
in one place:

    void <slug>_damage(<Slug> *s, int dmg);

  src/crucifaxe.c   Add a `static int <pfx>_hit_this_swing = 0;` beside the
                    others, clear it where the others are cleared, and add a
                    hit block modelled on the zombie's: Manhattan dist3d <
                    SWING_RANGE, then a `dot > 0` facing test, then knockback
                    (only if the enemy is in a state where being shoved makes
                    sense) and <slug>_damage(s, 1).

  src/graveolver.c  Add a targeting loop beside the others using
                    enemy_in_circle(x, y + <PFX>_Y_OFFSET, z, <PFX>_HALF_H,
                    fx, fz, &depth), guarded by `depth < best_depth &&
                    crosshair_clear(...)`. Claim the next free `best_kind`
                    value and add the matching dispatch branch calling
                    <slug>_damage(&<slug>s[best_idx], GUN_DAMAGE).

Both loops must skip enemies whose area != current_area (see STEP 6).
GUN_DAMAGE is 1 and a crucifaxe swing is 1, so "N hits to kill" == N health.


##########################################################################
 STEP 6 — PERSISTENCE: PICK THE RIGHT MODEL (THE SAVE BUDGET)
##########################################################################
>>> DECIDE THIS BEFORE WRITING world.c. IT IS EXPENSIVE TO GET WRONG. <<<

Two models exist:

  A. PER-ROOM (zombies, demon dogs, crates, pickups)
     The array lives in world.c's RoomState and is swapped on every
     world_leave/world_enter. Costs sizeof(array) x WORLD_NUM_ROOMS in the
     on-card blob — a copy in EVERY room, even the empty ones.

  B. GLOBAL + AREA-TAGGED (fat doors, tentacles, spiders)
     ONE array in the WorldState's global section. Each instance carries a
     `GameState area;` field and update/draw/weapon loops skip any instance
     whose area != current_area. Costs sizeof(array) ONCE.

     >>> current_area, NEVER game_state. <<< They are the same value during
     ordinary play and differ the moment the inventory menu opens: game_state
     becomes STATE_MENU while the room behind the menu keeps running (main.c
     passes current_area to update_current_area and draw_current_area). Gate on
     game_state and your enemy freezes and disappears for as long as the menu is
     up — the player can pause a fight by pressing Start, which no enemy in this
     game is meant to allow. It cost the Rabisu boss fight exactly that, and it
     is invisible until someone opens the menu mid-fight. The same rule applies
     to anything else that asks WHICH ROOM: a per-area table selected on
     game_state silently falls through to its default (zombies navigated the
     conservatory with the kitchen's zone tables for the same reason).

Use B unless the enemy genuinely needs per-room isolation. Model A puts a
fixed-capacity copy of the array in EVERY room, so 13 of the 14 copies are
empty; the Spider was written that way first and cost 2848 bytes of RAM against
Model B's 484. This is now a RAM argument only — the memory card no longer sees
these arrays at all (the WorldDelta stores one bit per instance) — but the RAM
argument alone still settles it. Check the cost with:

  mipsel-none-elf-nm.exe -S build\CMakeFiles\horror_game.dir\src\world.c.obj `
      | Select-String " world$"

For model B, wire world.c like this:
  - add `<Slug> <slug>s[MAX_<PFX>S]; int <slug>_count;` to WorldState, beside
    the tentacles, NOT to RoomState
  - mirror it in snapshot_fatdoors()
  - call <slug>s_rest() in world_leave() next to zombies_rest()
  - give it a field in WorldDelta (world.h) and handle it in BOTH halves of the
    codec at the bottom of world.c. A global area-tagged array must be keyed by
    canonical_index(), not by raw array index: the array is appended to as rooms
    are first entered, so a raw index means different things in two playthroughs
    that took different routes. Copy what the spiders do.
  - seed placements in world_enter()'s first-visit block (see STEP 7)

<slug>s_rest() rebuilds every living instance at its spawn, asleep, at full
health; deaths stick. Copy zombies_rest() — and remember to preserve the `area`
field across the `*s = (<Slug>){0};` wipe.

##########################################################################
 STEP 7b — NEW SOUND EFFECTS
##########################################################################
>>> CHECK THE SPU BUDGET FIRST. IT IS THE BINDING CONSTRAINT, NOT DISC SPACE. <<<
SPU RAM is 512 KB and it is nearly full. Measure the real footprint the way
sound.c's load_vag does — audio_size from each VAG header, rounded up to 64 —
and sum it from ALLOC_START (0x1010):

  for each VAG in sfx_files[]:  dma = (int.from_bytes(d[12:16],'big') + 63) & ~63

Adding the Spider's two clips (1.93 s + 1.44 s) needed ~40 KB against 6.4 KB
free. The fix was re-encoding the single biggest sound at half rate: zombie.vag
was 88 KB of low-frequency groan, and 11025 Hz freed 44 KB with no audible
loss. Prefer that to butchering the new clip. When you re-encode an existing
sound, keep its DURATION — the zombie's re-trigger interval (ZMB_GROAN_INTERVAL)
is tuned to sit just under the clip length, and shortening it opens a silent gap.

THE PIPELINE (mp3 -> wav -> vag), from sounds/:
    ffmpeg -y -i spdr_wlk.mp3 -ac 1 -ar 22050 -sample_fmt s16 spdr_wlk.wav
    py wav_to_vag.py spdr_wlk.wav --rate 22050 --loop    # looping ambience
    py wav_to_vag.py spit.wav     --rate 22050           # one-shot
sounds/mp3_to_wav.py is the documented first step but is BROKEN on Python 3.13+:
it needs pydub, which imports the stdlib `audioop` module that PEP 594 removed.
Call ffmpeg directly (as above) or install audioop-lts. wav_to_vag.py is pure
stdlib and resamples properly, so --rate really does change the footprint.

VERIFY THE LOOP FLAGS rather than trusting --loop. Byte 1 of each 16-byte ADPCM
block is the flag: a looping sample reads 0x06 on the first block and 0x03 on
the last; a one-shot reads 0x00 and 0x07.

WIRING:
  disc.xml       inside <dir name="SND">, 8.3 uppercase.
  src/sound.h    append the SfxID before SFX_COUNT and bump it. The enum order
                 MUST match sfx_files[] in sound.c.
  src/sound.c    add the path, and give any CONTINUOUS loop its own SPU voice in
                 sfx_channel(). The one-shot pool is FIRST_VOICE + (id % 8), so
                 a loop left in it gets cut off the moment an unrelated one-shot
                 lands on the same slot. Voices 16/17/18 are the zombie groan,
                 tentacle writhe and spider scuttle.

DRIVING A CONTINUOUS LOOP (copy the tentacle writhe, tentacle.c):
  A file-scope `static int <x>_on` plus a per-frame `any_<x>` flag, flipped by
  sound_play/sound_stop at the END of the update. ONE voice for all instances,
  not one per instance. Force the flag off on game_over — the area update stops
  running then, so the loop would otherwise stay keyed on forever.

##########################################################################
 THE MISTAKES THAT HAVE ACTUALLY BEEN MADE
##########################################################################
1. PROBING THE COLLISION PROXY FOR A HEIGHT THE PLAYER SEES. The proxy's wall
   tops are a lower bound, not the ceiling. The Spider hung a body length below
   the East Hall roof because the proxy stops at -375 and the drawn mesh is at
   -520. Read the VISUAL .smx, and record the value with
   collision_set_ceiling_y().

2. APPLYING GROUND_FLOOR_Y TO A CEILING. That constant converts a floor SURFACE
   into a standing ANCHOR; it is not a coordinate-space conversion. Subtracting
   it from a wall top put the Spider 149 units up through the roof. Entity
   coordinates and mesh coordinates are the same space.

3. GIVING AN ENEMY A PER-ROOM ARRAY WITHOUT CHECKING THE SAVE BUDGET. Seven
   empty copies of the array cost real memory-card space. Default to the global
   area-tagged model (STEP 6).

4. KEEPING THE ZOMBIE'S gte_nclip() BACKFACE CULL ON A SPRITE THAT ROLLS. Past
   90 degrees the winding flips and the sprite vanishes entirely.

5. ANCHORING A HANGING SPRITE BY ITS CENTRE OR ITS BOTTOM EDGE. Half in the
   ceiling, or entirely inside it. Anchor the TOP edge.

6. A TRANSITION ANIMATION LONGER THAN THE TRANSITION. The Spider's 18-frame
   upright roll outlasted a 13-frame fall, so it landed still rotating. Tie the
   frame count to the real distance and re-check it whenever that distance
   changes.

7. LEAVING THE LINE-OF-SIGHT SHORTCUT ON WHILE AN ENEMY RETREATS. It disables
   wall-following based on a sightline pointing the wrong way. Gate it on
   whether the enemy is actually moving toward the player.

8. A ZEROED COOLDOWN FIRING ON FRAME ONE. A fresh entity's timers are 0, so a
   `if (--timer <= 0) fire();` cooldown attacks the instant it first enters
   range. Arm the timer where the entity wakes.

9. SIZING A ROOTED ENEMY'S REACH WITHOUT CHECKING WHAT THE ROOM LETS THE
   PLAYER REACH. The Rafflesia was given a 150 pull radius and a 110 bite
   radius, straight off the design's "within 150". It was completely inert,
   and the reason is geometry, not code: its three flower beds are each tucked
   against a hedge, and the Outside Catacombs holds the player 260 off every
   wall (OC_WALL_RADIUS — wider than the usual 195 because its hedges are
   drawn 1100 tall). The closest the player can physically stand to those
   flowers is 110, 120 and 110 Manhattan. So `dist < 110` could not be true on
   any frame of any playthrough, and the 150 pull radius left a 30-unit sliver.

   >>> A ROOTED ENEMY'S REACH HAS A FLOOR, AND IT IS SET BY THE ROOM. <<<
   That floor is (the room's wall radius) minus (the enemy's distance from the
   nearest wall), and it applies to anything that cannot walk away from where
   it was planted. Two rules follow:
     - every attack radius must clear the floor by a real margin, not by a
       few units;
     - a HOLD distance (the range a pull settles at) must be ABOVE the floor,
       or the pull just grinds the player into the geometry forever.

   Check it, do not eyeball it. Parse the room's *_mesh_collision.c, sweep a
   grid, drop every point closer than the wall radius to any wall segment, and
   take the minimum distance to each spawn. That sweep is thirty lines and it
   would have caught this before the user ever saw it. Do the same whenever an
   enemy is replanted or a room's standoff changes.

10. AN ENEMY THAT PULLS THE PLAYER, WITHOUT A BODY TO STOP THEM. The Rafflesia
   hauled the player straight into its own billboard, where the quad crosses
   the GTE near plane and clips away — so the thing eating you was invisible,
   and being invisible it could not be aimed at either. ANY enemy that closes
   the distance for you needs a solid body; a stationary one the player chooses
   to walk up to can get away without one (the tentacle has none).

   Give it a CYLINDER (rafflesias_collide), not the crates' AABB — a billboard
   has no facing, so the stop distance must be identical from every bearing,
   and that needs a true radial test and a real integer sqrt. Size the radius
   from three constraints at once: outside the sprite half-width, inside the
   crucifaxe's SWING_RANGE so it stays meleeable while it holds you, and far
   enough back that the billboard still projects whole.

   >>> AND ORDER IT BEFORE THE WALL PASSES IN apply_collision_reception. <<<
   Every other prop there is pushed AFTER the walls, which is fine because they
   stand in open floor. An enemy planted against level geometry is not: its
   push circle overlaps the wall, and pushed last it wins and shoves the player
   INTO the hedge (measured: 949 of the standable cells around one flower did
   exactly that). Pushed first, the walls get the final say and the player is
   never wedged; the price is that in a tight pocket they end up closer to the
   enemy than its radius asked for. Hard world geometry beats a soft prop.

11. A DESCENDING-NEWTON isqrt SEEDED BELOW THE ROOT. `while (t > 1) { t >>= 2;
   s <<= 1; }` stops one shift early and seeds under the answer for every input
   that is not a perfect power of four; the loop's `while (x < last)` then fails
   on the first iteration and the function returns its own seed — isqrt(120)
   came back 8. Use `t > 0`, and check any integer sqrt against floor(sqrt)
   over a real range before trusting a distance built on it.

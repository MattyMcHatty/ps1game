PS1 HORROR GAME — ADDING A NEW ITEM: THE COMPLETE RUNBOOK
==========================================================
This is the authoritative, step-by-step procedure for adding a collectible item.
It was written immediately after the Flame Rounds were added (July 2026) and
records every step that was actually performed, in order, with real commands —
including the traps that a room/enemy addition does NOT have.

Companion docs (read them for the *why*; this file is the *how*):
  tools/ADDING_A_ROOM.txt           - the room runbook
  tools/ADDING_AN_ENEMY.txt         - the enemy runbook; this file mirrors both
  tools/TEXTURING_NOTES.txt         - VRAM rules, LoadImage timing, tex windows
  tools/VRAM_MAP.txt                - generated; who owns which VRAM slot
  rebuild commands.txt              - authoritative build steps


##########################################################################
 HOW TO KICK THIS OFF (what the user provides)
##########################################################################
To start an item addition, the user only needs to say:

  1. "Follow tools/ADDING_AN_ITEM.txt"
  2. The item's name, e.g. "Flame Rounds".
  3. The texture name, already dropped in textures/ as a PNG,
     e.g. flm_rnds.png.
  4. What it DOES when collected (see STEP 1 for the three kinds).
  5. Where to place it: room + x/z coordinates, and a quantity if it stacks.

Everything else — VRAM slot, CLUT line, menu slot, save wiring — is DERIVED by
the steps below.

NOTE ON PYTHON: the `python` on PATH is the Windows Store stub and fails. Use
`py` or the real interpreter explicitly:
    C:\Users\virtu\AppData\Local\Python\bin\python.exe


##########################################################################
 STEP 1 — DECIDE WHICH KIND OF ITEM IT IS
##########################################################################
There are three, and they cost very different amounts of work. Pick before
writing anything.

  A. A FLAG ITEM (copper pot, wax cube, green key stone)
     One bit in the player_items bitmask. Cheapest by far: a PickupKind, an
     ItemType, a menu slot. No save-format change — the bitmask already exists.

  B. A KEY (front door key)
     As A but in player_keys, and something in the world has to consume it.

  C. A COUNTED / STACKING ITEM (Standard Rounds, Flame Rounds)
     Carries an `amount`. This is the expensive one: it needs a counter in the
     player's inventory, a save-format field, and a HUD/menu count. If it is a
     new AMMO type it also needs STEP 4b and STEP 5.

The Flame Rounds were C plus a new ammo type — the fullest case, so the steps
below cover everything. Skip what does not apply.


##########################################################################
 STEP 2 — THE TEXTURE (THE ONE PLACE ITEMS ARE STRICTER THAN ENEMIES)
##########################################################################
>>> PICKUP SPRITES MUST LIVE AT Voff 0. THIS IS NOT TRUE OF ENEMY SPRITES. <<<

The enemy runbook says sprites MAY sit at Voff >= 128 because each one brackets
its own texture window. item_pickups_draw() does NOT bracket — it emits a plain
POLY_FT4 under whatever window the room set. So a pickup drawn in a room with
the usual 128x128 window must satisfy BOTH:

    Voff  (VRAM y % 256)  ==  0        ... and the sprite no taller than 128
    its U range within the tpage       ... must not cross 128

Put a pickup sprite at Voff >= 128 and it silently samples another texture's
art in every room that sets a window.

2a. Check the source PNG. 64x64 8bpp is the norm for pickups (matches
    stnd_rnds/graveolver). The art should fill the frame.

      py -c "from PIL import Image; im=Image.open('textures/flm_rnds.png'); \
             print(im.size, im.mode, im.getbbox())"

2b. Find a slot in tools/VRAM_MAP.txt. A 64px 8bpp sprite is 32 WORDS wide by
    64 tall. Work the widths out yourself — the map's "wpx" column is in PIXELS,
    so words = wpx/4 (4bpp), wpx/2 (8bpp), wpx (16bpp). The pickup band is the
    y=256 row, where the other pickup sprites live. Flame Rounds took
    x[480,512) y[256,320), the gap between din_cl and wd_dr_crk.

    A slot NOT on a 64-word page boundary is fine for a sprite: load_sprite()
    derives u0 from the texture's x within its page, so a sprite in the right
    half of a page maps correctly. Flame Rounds sits at u 64..127 of the page
    starting at VRAM x=448 — inside the 128 window, which is what matters.

2c. CLUT line: 8bpp needs 256 words, one line, y >= 480. Find a line whose only
    occupant is a 16-word 4bpp CLUT at x[0,16) and take x[256,512). Flame Rounds
    used (256,481), sharing y=481 with key.tim's 16-word CLUT.

2d. Convert:

      Set-Location "c:\Users\virtu\Documents\ps1game\textures"
      py png_to_tim.py flm_rnds.png --bpp 8 --tx 480 --ty 256 --cx 256 --cy 481 `
            --out flm_rnds.tim

2e. Regenerate the map and CHECK IT:

      py tools\vram_map.py | Out-File -Encoding utf8 tools\VRAM_MAP.txt
      Select-String tools\VRAM_MAP.txt -Pattern "UNEXPECTED|No unexpected|flm_rnds"

    Want "No unexpected pixel collisions." and your texture listed at Voff 0.

Items claim their VRAM permanently (item_pickups_load_textures LoadImages every
kind once at startup) — they are NOT time-shared like room art, so you do not
owe anybody a restore.


##########################################################################
 STEP 3 — THE PICKUP KIND
##########################################################################
  src/item_pickup.h  Add a PICKUP_<NAME> before PICKUP_KIND_COUNT.

  src/item_pickup.c  Add the matching row to BOTH tables — they are indexed by
                     PickupKind and MUST stay aligned:
                       kind_tim[]  -> "\\TEX\\FLMRNDS.TIM;1"
                       kind_name[] -> "Flame Rounds"   (the pickup-log line)
                     Then add a `case PICKUP_<NAME>:` to collect() granting
                     whatever STEP 4 decided.

  item_pickups_reset()  Clear the new counter/bit here. This runs on new game
                     and from crates_reset — an inventory field that is not
                     cleared here survives a "new game" and shows up in a fresh
                     playthrough.

MAX_ITEM_PICKUPS is 8 and pickups are per-room (world.c RoomState), so the cap
is per room, not global. Contrast the enemy runbook's spiders — that cap IS
global. Check which model an array uses before assuming.


##########################################################################
 STEP 4 — WHAT COLLECTING IT GRANTS (THE INVENTORY FIELD)
##########################################################################
  Kind A/B:  set a bit in player_items / player_keys (player.h). Nothing else.

  Kind C:    add a counter to player.h + player.c. If it is one of a FAMILY of
             counted things (ammo), make it an ARRAY indexed by a type enum
             rather than a second scalar — see STEP 4b. The single scalar
             `player_rounds` had to be torn out and replaced across seven files
             the moment a second ammo type existed; an array from the start
             would have cost nothing.


##########################################################################
 STEP 4b — A NEW AMMO TYPE (kind C, Grave-olver)
##########################################################################
Ammo is table-driven. Adding a type should touch the table and almost nothing
else.

  src/player.h   Add an AmmoType before MAX_AMMO_TYPES.
  src/player.c   Add its row to ammo_info[]:
                     { name, load_msg, damage_type, flash_r, flash_g, flash_b }
                 - name      : HUD label beside the cylinder count
                 - load_msg  : the pickup-log line when a swap completes
                 - damage    : the DamageType enemy weakness tables key on
                 - flash_*   : muzzle-flash colour, the visual tell for which
                               rounds are chambered. Keep types clearly distinct.

>>> PUT PER-TYPE BEHAVIOUR IN THE TABLE, NEVER IN A CONDITIONAL. <<<
The first cut of the "Loaded ..." message picked its wording by testing
`ammo_info[t].name[0] == 'F'`. That works for exactly two types and breaks
silently on the third. A `load_msg` column is the same amount of code and
scales.

THE CYLINDER holds ONE type at a time:
    player_ammo[MAX_AMMO_TYPES]   reserve, per type
    graveolver_ammo               the chambered type
    graveolver_loaded             rounds in the cylinder

SWAPPING (R2) costs a full reload. The design that keeps this simple is ONE
completion path for both cases (src/graveolver.c):
    reload_to     the type the cylinder will hold when the timer expires;
                  equals graveolver_ammo for an ordinary top-up
    swap_pending  1 only for a real type change — this is what makes the log
                  line fire on a swap and NOT on every reload
    reload_complete()  unloads the chambered rounds back into THEIR OWN reserve
                  first, then fills from the target's. Unloading first is what
                  stops a swap destroying part-used cylinders.

Sharing one path means the cancel case is automatically right: the cancel
(graveolver_cancel_reload, called by weapons_update on a weapon switch) clears
reload_timer, swap_pending AND reload_to, so an interrupted swap leaves the
cylinder at its existing count and type and posts nothing.

Gate the switch on availability: next_available_ammo() only returns a type the
player holds reserve rounds of, so R2 is inert in a single-ammo playthrough
instead of starting a pointless reload.

  src/debug_opts.c  Grant the new type in debug_opts_apply_grants() alongside
                    the others, so switching is testable from a level-select
                    jump without hunting for the pickup.


##########################################################################
 STEP 5 — ENEMY WEAKNESSES (only if the item changes damage)
##########################################################################
src/damage.h owns this. Ammo carries a DamageType; each enemy owns a table of
the types it is weak (or resistant) to.

  MODIFIERS ARE PERCENTAGES. 200 = double, 300 = triple, 50 = resistant.
  Percent rather than a whole multiplier so 150 (1.5x) needs no rework later.

  Adding a weakness is one line in the enemy's own .c:

      static const Weakness zombie_weakness[] = {
          { DMG_FLAME, 200 },
      };
      int32_t zombie_scale_damage(int32_t base, DamageType type) {
          return damage_scale(base, type, zombie_weakness,
                              WEAKNESS_COUNT(zombie_weakness));
      }

  EVERY enemy has one of these, even where the table is a
  `{ DMG_KINETIC, 100 }` placeholder, so a future weakness is a one-line edit
  and never a new function. Today: zombie (flame 200), tentacle (flame 300);
  spider / demon dog / vampire are placeholders.

  src/graveolver.c  Resolve the type ONCE per shot and pass the scaled amount
                    into each enemy's damage entry point:
                        DamageType t = ammo_info[graveolver_ammo].damage;
                        damage_zombie(z, zombie_scale_damage(GUN_DAMAGE, t));
                    Any enemy entry point that took no amount needs one adding
                    (tentacle_shoot gained its `amount` parameter here).

MELEE DOES NOT GO THROUGH THE TABLE. The crucifaxe has no damage type, and
giving it one would silently rescale every existing swing.


##########################################################################
 STEP 6 — THE INVENTORY MENU
##########################################################################
  src/menu.h   Add MENU_SLOT_<NAME> **at the END**, before MENU_ITEM_SLOTS, and
               bump MENU_ITEM_SLOTS. Appending avoids renumbering the existing
               slots, which are positional in several parallel arrays.

  src/menu.c   Five places, all indexed by the same slot number:
                 - the icon's tpage/clut/u0..v1 statics
                 - load_icon_tim(...) in menu_init()
                 - item_descriptions[] (order MUST match the slot numbering)
                 - items_count(), menu_item_held(), menu_item_name(),
                   menu_draw_item_icon()
                 - the grid draw loop's `i == <slot>` case, and the description
                   box's `slot == <slot>` case

  GRID CAPACITY: the ITEMS column draws 8 cells (2 cols x 4 rows, cursor rows
  0..3). Slots 5..7 are free today, so an item added now needs no layout change.
  Past 8 the grid itself has to grow.

  >>> THE STOVE PUZZLE SHARES THIS SLOT TABLE. <<<
  src/stove_puzzle.c iterates MENU_ITEM_SLOTS to build its ingredient picker, so
  a new slot appears there too. Its PICK_ROWS is computed from MENU_ITEM_SLOTS
  and so adjusts itself. Only the pot+cube pair is a valid combination, so a new
  item is selectable but inert — the same as Standard Rounds already were.
  Harmless, but look at the picker and confirm rather than assuming.


##########################################################################
 STEP 7 — HUD (counted items only)
##########################################################################
draw_hud() in src/player.c. The count under the stamina bar is drawn with the
built-in 3x5 pixel font (hud_draw_number, digits only). For TEXT beside it use
btn_prompt_draw(ctx, x, y, str, 0) — it renders via FntSort into the OT.

  Advance per digit at scale 2 is 8px (3*2 wide + 2 gap), so offset the label by
  digits*8 plus a gap; compute `digits` from the value rather than assuming one.

  TEXTURE WINDOW: FntSort is safe under a room's 128x128 window even though the
  HUD is sorted in front of the scene — the debug font's glyphs live in the top
  ~48 rows of its VRAM page, well inside the window. That is why the existing
  debug overlay renders correctly in every room. Do not add a speculative window
  reset; if you ever do need one, note that a DR_TWIN must be added AFTER the
  prims it should affect (LIFO within one OT node).


##########################################################################
 STEP 8 — PLACEMENT AND SAVE WIRING
##########################################################################
  src/world.c    In world_enter()'s first-visit block, beside the room's
                 enemies:
                     item_pickup_spawn_amount(x, y, z, PICKUP_<NAME>, count);
                 Use the _amount form and state the count explicitly rather than
                 relying on the ROUNDS_PER_PICKUP default, so a retune of that
                 constant cannot silently change a specified quantity.

                 Y: pass floor_y - 50 for a floor-level pickup in a y=0 room
                 (item_pickup_spawn adds IP_FLOAT_Y=50, putting the sprite just
                 above the boards), or -149 for chest height on furniture.

                 No save-blob cost: the ItemPickup array is fixed-size, so a new
                 KIND is free. A new inventory FIELD is not — see below.

  src/savegame.h >>> ANY NEW INVENTORY FIELD CHANGES SaveData. <<<
                 Add the field and BUMP SAVE_VERSION with a note saying what
                 changed. Old saves are then rejected cleanly. SaveData must
                 stay well under 128 bytes (one card frame); it is ~68 today.

  src/savegame.c Mirror the field in savegame_capture() and
                 savegame_apply_pending(). CLAMP anything used as an array index
                 on the way back in — a corrupt chambered-ammo value would index
                 ammo_info[] out of bounds in the HUD every frame.

  CMakeLists.txt Only if you added a new .c (damage.c was new here).

  disc.xml       Add the TIM inside <dir name="TEX">, 8.3 uppercase. Pickup and
                 icon TIMs go in TEX (contrast enemy sprite TIMs, which sit in
                 the ROOT). The ROOT directory must stay within one 2048-byte
                 sector or the disc will not boot.

##########################################################################
 STEP 10 — VERIFY
##########################################################################
Code-level checks before handing over:
  [ ] tools/VRAM_MAP.txt says "No unexpected pixel collisions" and the new
      texture is listed at Voff 0.
  [ ] kind_tim[] and kind_name[] are the same length as the PickupKind enum,
      and item_descriptions[] matches the menu slot numbering.
  [ ] Every old use of the field you replaced is gone:
          Select-String -Path src\*.c,src\*.h -Pattern "player_rounds"
      Stale COMMENTS count — they are what the next person reads.
  [ ] The _Static_assert in world.c still compiles.
  [ ] SAVE_VERSION was bumped if SaveData changed.

In-game (needs an emulator; say so plainly if you have not run it):
  [ ] The sprite shows the right art in the room it is placed in — wrong art
      means a Voff/texture-window problem (STEP 2).
  [ ] Collecting it posts the right pickup-log line and increments the count.
  [ ] The menu shows the icon, count and description in the right slot.
  [ ] Counted item: the HUD reads correctly at 1 and at 2+ digits.
  [ ] Ammo: R2 swaps only with a second type held; the reload animation plays
      in full; the message appears only on completion; switching weapons
      mid-swap keeps the ORIGINAL rounds; the muzzle flash is the right colour.
  [ ] Weaknesses: the weak enemy dies in the expected number of shots, and a
      non-weak one takes exactly as many as before.
  [ ] Save, reset, load: counts and the chambered type come back intact.


##########################################################################
 THE TRAPS THAT HAVE ACTUALLY BEEN HIT
##########################################################################
1. ASSUMING PICKUP SPRITES CAN SIT AT Voff >= 128 BECAUSE ENEMY SPRITES CAN.
   They cannot: item_pickups_draw does not bracket the texture window. Voff 0,
   and keep the U range inside 128.

2. A SCALAR WHERE A FAMILY WAS COMING. `player_rounds` as a single int had to be
   replaced across player/menu/savegame/item_pickup/debug_opts/graveolver/crate
   the moment a second ammo type existed. If an item is one of a kind that will
   plausibly have siblings, index it by an enum from day one.

3. PER-TYPE BEHAVIOUR CHOSEN BY SNIFFING A STRING. `name[0] == 'F'` to pick the
   log wording. Put it in the table.

4. FORGETTING THE SHARED SLOT TABLE. MENU_ITEM_SLOTS also drives the stove
   puzzle's ingredient picker.

5. ADDING AN INVENTORY FIELD WITHOUT BUMPING SAVE_VERSION. Old saves then load
   with the new field read from whatever those bytes used to mean.

6. NOT CLEARING A NEW FIELD IN item_pickups_reset(). It survives "new game".
